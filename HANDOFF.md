## Phase 1 - what exists (done)

The experiment at `/m/tuk-tuk-thai` in `apps/main`. No database, no auth. Full record with
verified tasks: `plan/main/menu-concierge/prototype.md`.

**Experience**
- QR lands on a warm greeting, three most-loved dish cards, one chilli question as chips.
- Each reply: 1 to 3 sentences, 0 to 4 dish cards, an optional question with tappable answers.
- Dish sheet: photo and video carousel, what arrives, tastes like (compared to Indian food),
  taste bars, numbered how-to-eat, story, ingredients, allergens and dietary badges, pairings,
  guest reviews, and chips that ask the host about that dish (answered in the thread).
- Full menu sheet and restaurant info sheet (ratings by platform, awards, hours, story).
- One explorer sheet: menu to dish to "goes well with" swap in place with a back pill; scroll
  position restored on back.
- Push-to-talk mic; the detected language is passed back so the host replies in kind. Voice is
  input only, nothing is spoken aloud at the table.
- Composer stays typeable while the host thinks; failed sends get a "Try again" chip.
- Printable table QR at `/m/tuk-tuk-thai/qr`.
- Light and dark, warm paper palette, Fraunces display font, grain texture. `menu.css` holds
  the tokens under `.tt`.

**Data and model**
- Knowledge base: `apps/main/data/restaurants/tuk-tuk-thai.json` - 26 dishes, 8 sections,
  ratings, review snippets, 79 verified Wikimedia Commons image and video URLs. Generated by a
  script that is not in the repo; edit the JSON directly.
- Host prompt: `apps/main/lib/menu/knowledge.ts`. The model returns one JSON object
  (`say`, `show`, `ask`, `remember`); the UI renders cards from dish ids. Parser with fallbacks
  in `lib/menu/protocol.ts`.
- Model: Sarvam `sarvam-105b` via `lib/menu/sarvam.ts`, JSON mode. **`reasoning_effort` must
  be `null`**; any other value spends the whole token budget on hidden reasoning and returns
  empty content. OpenAI had no credits; the plan is to move to OpenAI or Claude behind a
  provider switch (phase 2, doc 01 task 7).
- Speech to text: Sarvam `saaras:v4`, `language_code: unknown`, `mode: codemix`. The browser's
  `audio/webm;codecs=opus` is rejected by Sarvam, so the route re-wraps the bytes as
  `application/octet-stream` and Sarvam sniffs the format.
- Routes: `POST /api/menu/chat`, `POST /api/menu/stt`.

**Repo shape**
- `apps/main` - diner app (port 3000 in package.json, run on 5000 locally).
- `apps/tableadmin` - Tabled Admin, the restaurant owner's portal (port 3001). This is the
  renamed starter admin.
- `apps/admin` - Tabled Platform, a copy of the same admin for the Tabled team (port 3002).
- `packages/auth`, `db`, `storage`, `ui` - Better Auth, Drizzle, R2, Shadcn. All unused by the
  prototype but wired and ready.
- `plan/` - the task ledger. `CLAUDE.md` - stack, conventions, route and action reference.

**Known gaps**
- Typed Hinglish sometimes gets an English reply. Decided to leave until the model changes.
- The host occasionally repeats its question in `say` even with `ask` present; prompt forbids
  it, Sarvam still does it sometimes.
- A dev-only hydration warning from `next-themes` in the root layout predates this work.
- Wikimedia video is WebM; older iOS Safari may not play it.
- Niraj's own test pass (task 14) is still open; two findings have been fixed so far.

## Phase 2 - decided, not built

Everything is in `plan/main/taste-passport/`. Start with `questions.md`: 25 answers are
recorded inline with the date. Build order, each doc has tasks with acceptance criteria:

1. `01-foundation.md` - Neon Postgres, Better Auth for diners (Google + email magic link), R2,
   tables: `tasteProfile`, `visitIntent`, `tableSession`, `visitFeedback`, plus `restaurant`,
   `menuSection`, `dish`, `dishMedia`, `restaurantMember`, `dinerRestaurantShare`. LLM provider
   switch in one file. Seed from the JSON.
2. `04-host-knows-you.md` - known-diner opening (first name, 3 to 4 picks, at most one
   confirmation question, computed without a model call), the one-tap account nudge after the
   first shortlist (once per session, no form), table number from `?t=` on the QR URL, per-
   restaurant opt-in to share preferences, my-picks tray the waiter takes the order from.
3. `02-profile-and-onboarding.md` - profile learned from table conversations first (the
   host's `remember` notes promoted with a confirm tap), optional "tell me how you eat" voice
   note on the profile page. Four layers: hard constraints (confirmed by tap, never inferred
   silently), stable tastes (closed English vocabulary), situational, history. Dislikes are
   soft. Stored in English, shown in the diner's language.
4. `05-after-the-meal.md` - "was it what you expected?" on next open, three verdicts, private,
   may propose one profile change. Regret rate in both admin apps. This is the number the
   product is for.
5. `03-visit-intent.md` - "I'm heading to Tuk Tuk Thai" voice note before the visit. **Notes
   live forever as text** (Niraj's call), the newest unconsumed one is what the host reads.
   No push, no background job.
6. `07-restaurant-portal.md` - restaurant profile and menus in the database, menu scan via
   Sarvam document intelligence with the model structuring and the owner reviewing, dish image
   and video upload to R2, one QR per table, owner insights (aggregate; diner detail only when
   shared). Lives in `apps/tableadmin`. Ordering stays with the waiter.
7. `06-cloudflare-deploy.md` - Cloudflare Workers via OpenNext, Neon serverless driver, R2
   binding, GitHub Action. Durable Objects deferred until something outlives a request.

Key principles that came out of the questions: the restaurant is the customer; the diner account
is optional and comes from an in-chat nudge after the host has been useful; allergies are never
inferred; the restaurant sees aggregates by default; groups at a table are deferred but
`tableSession` is the hook.
